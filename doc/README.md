## 一、架构方案

### 1. 模块划分

> 待 P10 补全：每个模块（目录）的职责表 + PlantUML 组件图/包图。

| 模块 | 职责 | 不允许做的事 |
|---|---|---|
| `src/cli/` | REPL 循环、分词、输入输出 | 直接修改图形数据 |
| `src/commands/` | Command 接口与各具体命令、命令栈 | 包含业务逻辑（只转发） |
| `src/model/` | 图形类层次、文档模型（Receiver） | 打印、读文件、认识 CLI |
| `src/io/` | SVG 读写（序列化/反序列化） | 修改内存中的文档结构 |

### 2. 设计模式的选择

> 待 P10 补全：问题 → 方案 → 模式名称，以及 Command 在代码中的落地位置。

- **Command（行为型）**：解决的问题是"请求要能被保存并重放"（undo/redo）。落地位置：`src/commands/`。
- **Composite（结构型）**：解决的问题是"容器与叶子统一操作"（`<g>` 与 `<rect>` 一视同仁）。落地位置：`src/model/`。

### 3. 依赖方向规则

> 待 P10 补全：明确写出"哪些模块可以依赖哪些模块"，并说明理由。

约定（草案）：

```text
cli  →  commands  →  model
cli  →  io        →  model
```

反向依赖视为待处理项：`model` 不得 import `cli` / `commands`；`model` 不得 import `io`。

### 4. 变化点假设

> 待 P10 补全：逐条列出"未来最可能变化的地方"，以及为它留了什么（或为什么决定不留）。

- 建了 TypeScript 工程（`tsc` 编译、`tsx` 直跑、Vitest 测试），`src/cli/` 下先落地 `Repl` 与 `Tokenizer` 两类。
